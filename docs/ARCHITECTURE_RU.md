# Архитектура CLIRadar

## Назначение

CLIRadar исследует CLI-синтаксис сетевого устройства через интерактивную
контекстную справку `?`. Это один консольный процесс без GUI, web-сервиса,
очередей и базы данных.

Инструмент:

1. в режиме `docs` строит каталог документации без SSH;
2. в режиме `compare` сопоставляет полное дерево устройства с документацией;
3. в режиме `audit` сохраняет полный доступный каталог устройства;
4. никогда не завершает найденную команду нажатием Enter;
5. сохраняет нормализованные YAML-каталоги и автономный HTML-отчёт сравнения.

CLIRadar не входит в configuration submode, не обходит авторизацию и не является
CVE-сканером.

## Структура

```text
cliradar/
├── src/cliradar/
│   ├── cli.py         # argparse, сценарий и безопасная запись артефактов
│   ├── config.py      # типизированная YAML-конфигурация
│   ├── crawler.py     # BFS и подстановка значений параметров
│   ├── docs.py        # извлечение команд из документов
│   ├── exceptions.py  # ожидаемые ошибки приложения
│   ├── export.py      # дерево токенов и человекочитаемый список команд
│   ├── models.py      # HelpOption, CommandEntry, Catalog
│   ├── modes.py       # контракт навигатора и crawler, обход графа контекстов
│   ├── navigator.py   # отпечаток промпта, вход и выход из режимов
│   ├── parser.py      # разбор вывода контекстной справки
│   ├── report.py      # автономный HTML-отчёт отсутствующих команд
│   └── session.py     # интерактивная SSH-сессия
├── tests/
├── docs/
├── vendor_docs/
├── config.example.yml
└── pyproject.toml
```

Парсер, обработчик документов и crawler не зависят от SSH и тестируются на
строках и scripted channel.

## Два потока данных

```text
online-режимы:
root "?" -> BFS по доступным веткам -> полный каталог устройства

docs:
vendor_docs/* -> scan_documentation() -> output/cli_doc.yml

compare:
vendor_docs/* -> scan_documentation() ----+
                                         |
каталог устройства -----------------------> сравнение -> output/cli_compare.yml
                                                        └-> missing_commands.html

audit:
raw help -> parse_context_help() -> Catalog -> output/cli_real.yml
```

Корневой `?` всегда является первым запросом. В `compare` документация
накладывается на полный каталог, а её команды выполняются как отложенные
точечные запросы после основного дерева. Такие проверочные запросы только
подтверждают наличие команды: их ответы не порождают новых узлов обхода,
иначе синтаксические варианты из документации приводили бы к комбинаторному
взрыву. В `audit` документация не читается. Режим `docs` не импортирует
SSH-сессию и не подключается к устройству.

## Документация

`scan_documentation()` рекурсивно читает `.txt`, `.md` и `.rst` размером до
5 МиБ. Символьные ссылки пропускаются.

Распознаются:

- одна команда на строку в `.txt`;
- команда и описание, разделённые Tab или двумя пробелами;
- блоки синтаксиса после `Command Format`, `Command Form`, `Command Syntax`,
  `Syntax`, `Формат команды` и `Синтаксис` в конвертированных `.txt`
  справочниках;
- переносы внутри синтаксиса, обязательные варианты `{a | b}` и необязательные
  группы `[optional]`;
- `Command:`, `Syntax:`, `Usage:` и `Example:`;
- строки с prompt вида `switch# show version`;
- fenced code blocks;
- Markdown-таблицы.

Кандидат должен быть печатным ASCII-префиксом длиной не более 512 байт и не
содержать `?`. Строки `sudo`, `ssh` и `telnet` отбрасываются.

Документированная команда сначала имеет только источник
`documentation:<path>`. После запроса устройство добавляет источник `cli`, если
парсер увидел допустимое продолжение или `<cr>`.

## Разбор справки

`clean_terminal_output()` удаляет ANSI-последовательности, возвраты каретки и
эффекты Backspace.

`parse_context_help()`:

1. удаляет prompt и echo запроса;
2. игнорирует типовые ошибки `Invalid`, `Unknown`, `Unrecognized` и `% ...`;
3. делит строку на token и description по Tab или двум пробелам;
4. классифицирует token как `keyword`, `parameter` или `cr`;
5. удаляет дубликаты.

`<cr>` помечает текущий префикс исполняемым, но Enter не отправляется.

## Crawler

`crawl()` использует breadth-first search. Узел очереди содержит два префикса:

- `catalog_prefix` — шаблон, который попадёт в YAML;
- `query_prefix` — реальные символы, отправляемые устройству.

Для обычного keyword они совпадают. Для параметра различаются:

```text
catalog_prefix: show vlan <1-4094> brief
query_prefix:   show vlan 1 brief
```

Нижняя граница числового диапазона выбирается автоматически. Остальные примеры
берутся из `discovery.parameter_samples`. Наличие ключа в этом mapping также
помечает строчный token документации как параметр. Если значения нет, параметр
сохраняется, но ветка не раскрывается. Literal-плейсхолдер устройству не
отправляется.

За завершение отвечают:

- пустая очередь;
- `max_queries`;
- `max_depth`;
- callback отмены;
- необязательный `denied_tokens`.

`visited` хранит пару каталогового и фактического префиксов, поэтому циклические
или повторные запросы не разрастаются бесконечно.

При `discovery.parallel_channels > 1` обход выполняется пулом потоков: каждый
поток владеет собственным shell-каналом той же SSH-сессии, а очередь, каталог
и счётчики защищены одним condition-объектом. Отложенные проверочные сиды
стартуют только после полного исчерпания основного дерева, как и в
последовательном режиме. Ошибка любого потока останавливает остальные и
пробрасывается вызывающему коду.

## Модель результата

`HelpOption` содержит token, description и kind.

`CommandEntry` содержит:

- нормализованную команду;
- описание;
- множество источников;
- признак `executable`;
- дочерние команды.

В `compare` источник `cli` считается истиной:

- `matched` — есть `cli` и `documentation:*`;
- `undocumented` — есть только `cli`;
- `missing_on_device` — есть только документация и обход завершён полностью;
- `not_observed` — есть только документация, но обход неполон.

В `audit` найденные элементы получают `device_status: present`.
В `docs` извлечённые элементы получают `documentation_status: parsed`.

`Catalog` записывает schema version 3, режим, скрытую identity устройства,
timestamp, сведения о полноте `scan`, итоговые счётчики `summary` и команды в
стабильном порядке.

## SSH-сессия

`SwitchSession`:

1. читает пароль из переменной окружения;
2. проверяет SSH host key и отклоняет неизвестный;
3. отключает `ssh-rsa`;
4. открывает интерактивный PTY;
5. ждёт prompt;
6. для запроса отправляет `Ctrl-U`, `prefix + "?"`, затем снова `Ctrl-U`.

`query_help()` не отправляет `\n` или `\r`. Префикс должен быть печатным ASCII,
не содержать `?` и занимать не более 512 байт. Один ответ ограничен
`max_response_bytes`.

`open_extra_channels()` открывает дополнительные shell-каналы поверх того же
SSH-транспорта для параллельного обхода. Если устройство отказывает в
очередном канале, открытие молча прекращается и сканирование продолжается с
меньшим числом потоков. Запись raw log сериализуется общим lock.

В POSIX raw log и каталог записываются с режимом `0600`; в Windows они наследуют
ACL каталога. Запись через symlink запрещена.

## CLI и конфигурация

Основные команды:

```text
cliradar compare --config config.yml --docs vendor_docs
cliradar audit --config config.yml
cliradar docs --config config.yml --docs vendor_docs
cliradar --config config.yml --check-config
```

Для online-режима CLI читает пароль только из переменной процесса, указанной в
`device.password_env`.

`load_config()` использует `yaml.safe_load()` и валидирует SSH-поля, regex
prompt, timeout, лимиты, seed-команды и parameter samples до подключения.

Коды завершения:

- `0` — успех;
- `2` — аргументы или конфигурация;
- `3` — SSH/интерактивная сессия;
- `4` — сканирование или файловая система.

## Ограничения

Нельзя получить буквально все команды любого устройства одним универсальным
алгоритмом:

- часть дерева доступна только после входа в другой CLI-контекст;
- параметры требуют существующих значений;
- справка может зависеть от прав и состояния конфигурации;
- разные NOS используют разные prompt, erase-line и pagination.

Поэтому полнота означает: все ветки, доступные текущей учётной записи и
контексту, которые удалось раскрыть в пределах лимитов и настроенных примеров.
Поддержка configuration submode должна добавляться отдельным явным профилем,
который перечисляет разрешённые переходы, а не выполнением произвольно найденных
команд.

## Проверки

```bash
ruff check .
pytest
bandit -q -r src
pip-audit
python -m build --no-isolation
```

Изменения парсера и crawler должны сопровождаться regression-тестом. Новый тип
устройства сначала проверяется на лабораторном стенде с анализом raw log.
