# Эксплуатация CLIRadar

## Подготовка

1. Создайте на устройстве отдельную учётную запись только для чтения.
2. Добавьте SSH host key устройства в `known_hosts`.
3. Установите проект: `python -m pip install .`.
4. Скопируйте `config.example.yml` в `config.yml` и укажите host, username,
   prompt и лимиты.
5. Передайте пароль через переменную процесса. Её имя должно совпадать с
   `device.password_env`.

Готовое виртуальное окружение в проект не входит и не коммитится.

Проверка конфигурации без подключения:

```bash
cliradar --config config.yml --check-config
```

## Режим `docs`

Разобрать локальную документацию без SSH:

```bash
cliradar docs --config config.yml --docs vendor_docs
```

Режим не требует `device.host`, `device.username` и пароля. Результат
записывается в `output/cli_doc.yml`.

## Режим `compare`

Сложите `.txt`, `.md` или `.rst` в `vendor_docs/`. Надёжнее всего работает
обычный список с одной командой на строку. Допустимы строки с prompt, метки
`Command:`/`Syntax:` и описание после двух пробелов.

Сопоставить документацию с полным деревом команд устройства:

```bash
cliradar compare --config config.yml --docs vendor_docs
```

Режим начинает с корневого `?` и сначала строит полное доступное дерево
устройства. Команды документации используются для сравнения и дополнительных
точечных проверок после основного обхода; проверочные запросы не раскрывают
ветки вглубь.

Во время обхода в терминале обновляется строка прогресса с процентом,
размером очереди и оценкой оставшегося времени; `--quiet` её отключает.
Для ускорения задайте несколько параллельных каналов:

```yaml
discovery:
  parallel_channels: 4
```

Каналы открываются внутри одной SSH-сессии. Если устройство разрешает меньше
каналов, сканирование продолжается с доступным количеством.

## Режим `audit`

Полный обход доступного из текущего CLI-контекста дерева:

```bash
cliradar audit --config config.yml
```

Сканирование останавливается при исчерпании дерева, `max_queries` или
`max_depth`. Для пропуска отдельных веток заполните `denied_tokens`.

Если справка возвращает параметр, а не ключевое слово, нужен пример значения.
Числовые диапазоны обрабатываются автоматически. Для остальных типов добавьте
образцы:

```yaml
discovery:
  parameter_policy: explore
  parameter_samples:
    WORD: Ethernet1/1
    A.B.C.D: 192.0.2.1
```

Проверяйте, что пример действительно существует на устройстве. Если один и тот
же token используется для разных сущностей, запускайте отдельные проходы с
разными примерами и сохраняйте результаты под разными именами.

## Режимы конфигурации (`--enter-modes`)

```bash
cliradar audit --config config.yml --enter-modes
```

Это **единственный режим, который выполняет команды на устройстве**. Вход в
контекст — уже выполнение: на многих платформах `vlan 10` не открывает
просмотр, а создаёт VLAN. Первый прогон на новом типе устройства делайте
только на стенде, который не жалко сбросить.

Порядок работы:

1. Убедитесь, что железка лабораторная и её конфигурация не нужна.
2. Запустите прогон. Живая строка прогресса дополняется строкой на каждый
   найденный контекст.
3. После прогона откройте HTML-отчёт и прочитайте два блока: «Контексты CLI» —
   что найдено, и «Выполненные команды» — что именно было нажато с Enter.
4. Сбросьте устройство или откатите изменения по этому списку.

Что ограничивает изменения:

- команды из денилиста проб (`reboot`, `erase`, `logout`, `ping`, `terminal`
  и подобные) не выполняются никогда;
- универсальные заглушки параметров (`WORD`, `NAME`, `STRING`, `PASSWORD`)
  не подставляются: пример для такой заглушки подходит к сотням несвязанных
  команд. Конкретные (`IFNAME`, `A.B.C.D`) подставляются — они называют уже
  существующий объект;
- число проб на контекст ограничено (`max_probes_per_context`, по умолчанию
  200); порядок ставит вероятных «открывателей режимов» первыми, а количество
  непробованных кандидатов попадает в отчёт как `probes_skipped`;
- запрос подтверждения (`[y/n]`) получает ответ «нет».

Если прогон прервать принудительно, SSH-сессии остаются висеть на устройстве
до истечения его таймаута, и следующий запуск может получить отказ. Дайте
железке время либо освободите линии через консоль.

**Проба меняет дерево, которое измеряет.** Созданный пробой объект (например
`filter-list 1`) добавляет в CLI команды работы с ним, и следующий прогон их
найдёт. Поэтому два прогона подряд не обязаны совпадать до команды; сравнение
«до и после» корректно только между одинаковыми состояниями устройства.

## Артефакты

- `output/cli_doc.yml` — команды, извлечённые режимом `docs`;
- `output/cli_real.yml` — реальный каталог устройства из `audit`;
- `output/cli_compare.yml` — совмещённый результат `compare`;
- `output/missing_commands.html` — автономная страница отсутствующих команд из
  `compare`;
- `output/commands_tree.yml` — вложенное дерево токенов (ключ = слово,
  лист = пусто); в online-режимах — команды устройства, в `docs` — команды
  документации;
- `output/commands_human.yml` — плоский список «команда: что она делает» по
  алфавиту, из того же источника, что и дерево;
- в каталоге режима `--enter-modes` команды контекстов записаны полным путём
  от корня (`configure vlan 1 name`), а раздел `scan` содержит список
  контекстов, `executed_commands` и `probes_skipped`;
- `output/session.log` — необработанная справка, только если задан
  `output.raw_log`.

HTML-страница содержит только подтверждённые `missing_on_device`. При неполном
обходе она вместо этого показывает `not_observed` и предупреждение. Страница
включает строку поиска по командам и описаниям со счётчиком совпадений. Путь
задаётся полем `output.html_report`; стили и скрипт встроены, внешние ресурсы
не загружаются.

В режиме `compare`:

- `comparison_status: matched` — команда есть в обоих источниках;
- `comparison_status: undocumented` — команда найдена на устройстве, но не в
  документации;
- `comparison_status: missing_on_device` — документация содержит команду,
  которой нет в полном результате устройства;
- `comparison_status: not_observed` — команда не найдена, но обход неполон.

В режиме `audit` все найденные команды имеют `device_status: present`.
В режиме `docs` извлечённые команды имеют `documentation_status: parsed`.

Поле `scan.complete` равно `false`, если сработал лимит, максимальная глубина,
отмена, deny-правило или встретился параметр без рабочего примера. В таком
случае отсутствие команды нельзя считать доказанным.

В POSIX файлы создаются с режимом `0600`; в Windows наследуют ACL родительского
каталога. Они могут содержать внутренние команды и описания, поэтому не
публикуйте их.

## Коды завершения

| Код | Значение |
| --- | --- |
| `0` | Успешное выполнение |
| `2` | Ошибка аргументов или конфигурации |
| `3` | Ошибка SSH или интерактивной сессии |
| `4` | Ошибка сканирования или файловой системы |

## Диагностика

`configuration error` означает, что подключение ещё не началось.

`connection error` обычно означает одну из причин:

- host key отсутствует или изменился;
- неверные username/password;
- устройство не поддерживает разрешённые SSH-алгоритмы;
- prompt не соответствует `device.prompt_pattern`;
- устройство не отвечает в пределах timeout.

`not_observed` означает, что результат неполон. Проверьте `scan`, настройте
`parameter_samples`, увеличьте лимиты и при необходимости включите
`output.raw_log`.

`derived_mismatched` в разделе `scan` — узел, поддерево которого было выведено
по совпадению формы, при проверке ответил иначе. Обход помечается неполным.
Если таких узлов много, отключите `discovery.deduplicate_subtrees` и сравните
результаты: это означает, что грамматика платформы повторяет форму, но не
содержание.

`unreachable_contexts` — режим, в который не удалось попасть даже после
переподключения. Обычно это команда входа, переставшая работать после
изменений, внесённых самими пробами.

## Приёмка на новом типе устройства

1. Запустите оба online-режима (`audit` и `compare`) на лабораторном устройстве.
2. Включите `output.raw_log` и убедитесь, что формат справки корректно
   распознаётся, а отправляются только `Ctrl-U`, префикс, `?` и пробел для
   продолжения пагинации.
3. Проверьте на стенде отсутствие побочных эффектов `?`; рискованные ветки
   добавьте в `denied_tokens`.
4. Проверьте корневую и длинную справку, пагинацию и erase-line.
5. Подберите `parameter_samples`, включая строчные плейсхолдеры документации.
6. Проверьте остановку по глубине и числу запросов.
7. Проверьте, что после ответа на `?` устройство перерисовывает строку
   (приглашение и заново набранный префикс): на таких платформах обход идёт на
   порядок быстрее. Если нет — обход работает, но медленнее, через
   `device.idle_timeout`.
8. Только после этого пробуйте `--enter-modes`, и только на устройстве,
   которое можно сбросить.
7. Повторите запуск и сравните стабильность YAML.
